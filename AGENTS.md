# AGENTS.md

# Graber AI Development Guide

## Project Overview

Graber — Telegram-бот на C# (.NET), предназначенный для скачивания медиа с различных сервисов и отправки его пользователю.

Текущий стек:

- .NET
- Telegram.Bot
- FFMpegCore
- FFprobe
- HLS (.m3u8)
- Dependency Injection
- Clean Architecture

---

# Primary Goal

Главная цель проекта — поддерживаемый и расширяемый код.

При возникновении конфликта между:

- "быстро написать"
- "сделать правильно"

предпочитать второй вариант, если это не приводит к чрезмерному усложнению.

---

# Architecture

Проект следует принципам Clean Architecture.

Слои:

Presentation
Application
Domain
Infrastructure

Правило зависимостей:

Presentation
↓

Application
↓

Domain

Infrastructure зависит только от Application и Domain.

Domain никогда не зависит от Infrastructure.

Не нарушать это правило.

---

# Responsibilities

## Presentation

Содержит:

- Telegram handlers
- Commands
- Bot interaction

Не содержит бизнес-логику.

Допустимо:

- преобразование Update → Command
- обработка ошибок
- логирование

Недопустимо:

- работа с FFmpeg
- работа с HTTP
- выбор алгоритмов
- бизнес-правила

---

## Application

Содержит:

- Use Cases
- Interfaces
- DTO
- Services
- Orchestration

Application определяет:

что должно быть сделано.

Application НЕ знает:

- EF Core
- Telegram
- FFmpeg
- HTTP
- файловую систему

Application работает только через интерфейсы.

---

## Domain

Domain содержит:

- Entities
- Value Objects
- бизнес-правила

Domain ничего не знает:

- о Telegram
- о FFmpeg
- о JSON
- о HttpClient
- о FFMpegCore

---

## Infrastructure

Infrastructure содержит реализацию интерфейсов.

Допустимо:

- FFmpeg
- FFprobe
- HttpClient
- файловая система
- Telegram API
- внешние сервисы

# Current Download Pipeline

На момент написания документа pipeline выглядит следующим образом:

User URL

↓

Service Detector

↓

Service Downloader

↓

Playlist Selection

↓

FFmpeg Download

↓

Metadata Extraction

↓

Telegram Upload

При изменении pipeline сначала понять текущий поток данных.

Не предлагать масштабный рефакторинг без необходимости.

---

# MetadataExtractor

MetadataExtractor отвечает ТОЛЬКО за чтение информации из уже существующего медиа.

Он НЕ отвечает за:

- выбор playlist
- скачивание
- выбор качества
- объединение потоков

MetadataExtractor должен корректно работать даже если:

- отсутствует видео
- отсутствует аудио
- несколько video stream
- несколько audio stream

---

# HLS

При работе с HLS учитывать:

master playlist

↓

media playlist

↓

segments

Не предполагать, что ссылка уже указывает на видео.

Если проблема связана с отсутствием видеопотока — сначала проверить выбор playlist, а не MetadataExtractor.

---

# FFmpeg

Использовать FFMpegCore.

Не вызывать ffmpeg напрямую без необходимости.

При работе с FFmpeg:

- учитывать существование нескольких потоков
- не предполагать наличие PrimaryVideoStream
- учитывать контейнер отдельно от codec

---

# Dependency Injection

Все сервисы должны регистрироваться через DI.

Не использовать Service Locator.

Не создавать static сервисы.

Singleton использовать только если это действительно безопасно.

---

# Async

Все IO операции должны быть async.

Не использовать:

Task.Result

Wait()

GetAwaiter().GetResult()

если этого можно избежать.

---

# Logging

При возникновении ошибок:

предпочитать информативные сообщения.

Не скрывать исключения без причины.

---

# Error Handling

Если возможно продолжить работу — использовать Result вместо исключений.

Исключения использовать только для действительно исключительных ситуаций.

---

# Code Style

Использовать:

- file-scoped namespaces
- nullable reference types
- primary constructors (если улучшают читаемость)
- expression-bodied members только когда это действительно проще

Не использовать:

- #region
- длинные методы
- глубокую вложенность

Предпочитать ранний выход (guard clauses).

---

# Design Principles

Предпочитать:

SOLID

KISS

YAGNI

Composition over inheritance

---

# New Services

Перед созданием нового сервиса определить:

1. какая у него ответственность;
2. в каком слое он должен находиться;
3. нельзя ли расширить существующий сервис.

Не создавать интерфейс только "на будущее".

Интерфейс нужен если:

- есть несколько реализаций;
- ожидается подмена;
- требуется тестирование через абстракцию.

---

# Refactoring Policy

Не проводить большой рефакторинг при выполнении локальной задачи.

Если найден архитектурный долг:

- описать проблему;
- предложить варианты;
- дождаться подтверждения.

---

# Issue and Branch Workflow

Каждый новый roadmap-этап начинать до внесения изменений в код:

1. Определить цель и границы этапа.

2. Если доступен GitLab или другой issue tracker репозитория, найти существующий issue по названию и ключевым словам этапа. Проверять открытые и закрытые issue, чтобы не создавать дубликаты.

3. Если подходящего issue нет и доступна авторизация, создать issue с:

- контекстом и проблемой;
- ожидаемым результатом;
- границами задачи;
- критериями приёмки.

4. Если поиск или создание issue технически недоступны, явно сообщить об этом пользователю перед продолжением и не утверждать, что issue отсутствует.

5. Перед реализацией проверить текущую Git-ветку и убедиться, что работа ведётся в отдельной task-ветке, созданной от `develop` для этого issue.

6. Использовать существующее соглашение об именовании веток. Если соглашения нет, использовать формат:

```text
feature/<issue-number>-<short-slug>
```

7. Номер issue должен быть прослеживаем из имени ветки или явно зафиксирован в описании работы.

8. Не начинать реализацию нового этапа напрямую в `develop` или `master`.

9. Если нужной ветки нет, создать её от `develop`, только если состояние worktree позволяет безопасно переключиться. Не выполнять автоматический `stash`, `reset`, `rebase` или перенос незакоммиченных изменений.

10. Если незакоммиченные изменения не позволяют безопасно создать или переключить ветку, остановиться, описать состояние и запросить решение пользователя.

Эти действия выполняются один раз в начале этапа. Для последующих изменений в рамках того же issue повторно создавать issue или ветку не нужно.

---

# Working Style

Перед внесением изменений:

1. понять текущую реализацию;
2. определить тип задачи;
3. объяснить trade-offs;
4. только потом менять код.

Если решение неоднозначное — сначала обсудить архитектуру.

---

# Educational Mode

По умолчанию использовать режим обучения.

Предпочтительный стиль взаимодействия с разработчиком:

Не писать готовый код, если пользователь явно не попросил.

Вместо этого:

1. определить тип задачи;

2. объяснить концепцию;

3. объяснить применяемый паттерн;

4. задавать наводящие вопросы;

5. направлять к решению;

6. после реализации провести code review.

Допускается писать готовый код только если пользователь явно попросил.

---

# Code Reviews

При review оценивать:

- читаемость;
- архитектуру;
- ответственность классов;
- тестируемость;
- расширяемость;
- соответствие Clean Architecture.

Не ограничиваться поиском ошибок.

Предлагать улучшения с объяснением trade-offs.

---

# Communication Style

Предпочитать:

- краткие объяснения;
- техническую терминологию;
- аргументацию решений;
- обсуждение нескольких вариантов.

Не навязывать рефакторинг.

Не менять стиль проекта без необходимости.

Не предлагать новые библиотеки, если существующие уже решают задачу.

---

# Project Priority

Приоритеты:

1. Корректность.
2. Архитектура.
3. Простота поддержки.
4. Производительность.
5. Красота кода.

Если приходится выбирать между "умным" и "понятным" кодом — выбирать понятный.
