# Graber Architecture Decisions

Документ содержит только решения, уже принятые для проекта. Предложения и неподтверждённые варианты находятся в `ROADMAP.md`.

## ADR-001: Использовать Clean Architecture

**Статус:** принято.

Проект разделяется на Presentation, Application, Domain и Infrastructure.

Направление зависимостей:

```text
Presentation → Application → Domain
Infrastructure → Application → Domain
```

Domain не зависит от Infrastructure. Внешние технологии остаются в Infrastructure или Presentation.

## ADR-002: Использовать Dependency Injection

**Статус:** принято.

Сервисы регистрируются через DI. Service Locator и static services не используются. Telegram worker создаёт scope на обработку сообщения.

## ADR-003: Передавать ожидаемые ошибки через Result

**Статус:** принято.

Ожидаемые ошибки application pipeline возвращаются через `Result<T>`. Исключения предназначены для действительно исключительных ситуаций и преобразуются в application errors на границах инфраструктуры.

## ADR-004: Расширять поддержку сервисов через scraper-реализации

**Статус:** принято.

Подходящий scraper выбирается через `ScraperProvider` и `CanExecute`. Текущая реализация поддерживает X. Добавление новых сервисов выполняется дополнительными реализациями контракта scraper.

## ADR-005: Scraper обнаруживает источник, Application оркестрирует pipeline

**Статус:** принято, ещё не полностью реализовано.

Целевая ответственность scraper — обнаружение media source для конкретного внешнего сервиса.

Application отвечает за orchestration:

```text
service detection
→ source discovery
→ downloader selection
→ download
→ metadata extraction
→ result construction
```

Текущая orchestration внутри `XScraper` является временным состоянием и должна переноситься небольшими проверяемыми этапами.

## ADR-006: Использовать HLS и FFmpeg через FFMpegCore

**Статус:** принято.

HLS media скачивается через FFMpegCore. Прямой вызов процесса FFmpeg не используется без отдельной необходимости. Текущий pipeline remux-ит потоки в MP4 без перекодирования.

## ADR-007: MetadataExtractor только читает существующее медиа

**Статус:** принято.

MetadataExtractor не выбирает playlist, качество или алгоритм скачивания. Он читает metadata из уже существующего медиа и должен учитывать отсутствие и множественность video/audio streams.

## ADR-008: Выбирать рациональное низкое или среднее качество

**Статус:** принято на уровне продукта; точное правило ещё предстоит определить.

Максимальное качество не является целью по умолчанию. Приоритет отдается рациональному низкому или среднему профилю, чтобы ограничивать время скачивания и размер результата.

Точное детерминированное правило фиксируется после исследования доступных HLS-профилей.

## ADR-009: Ограничить максимальный размер видео

**Статус:** принято; числовой предел ещё не определён.

Pipeline не должен допускать неконтролируемое потребление памяти при скачивании больших видео. Необходимо установить максимальный размер и прекращать обработку контролируемым способом при его превышении.

## ADR-010: Отправлять результат как Telegram video

**Статус:** принято, ещё не реализовано.

Целевой способ отправки — Telegram video со встроенным воспроизведением, а не document. Короткие видео должны отображаться как воспроизводимое медиа без требования ручного скачивания пользователем.

## ADR-011: Использовать headless Chromium в production

**Статус:** принято, ещё не реализовано.

Production scraping выполняется в headless mode. Подготовка Chromium должна быть идемпотентной: повторная проверка допустима, повторное скачивание уже установленной ревизии не требуется.

## ADR-012: Семантика ошибок загрузки страницы и playlist

**Статус:** принято.

Если страница X не загрузилась или `.m3u8` не был получен за установленное время, application result — `NotFoundVideo`.

## ADR-013: Не наполнять Domain искусственными моделями

**Статус:** принято.

Domain остаётся минимальным, пока в приложении нет подтверждённых бизнес-правил и инвариантов. Новые domain abstractions не создаются только для формального наполнения слоя.

## ADR-014: Сохранить MediaDownloaderProvider

**Статус:** принято.

`MediaDownloaderProvider` сохраняется как механизм выбора downloader при появлении нескольких реализаций и должен использоваться application orchestration.

## ADR-015: Отделять внешние integration-тесты

**Статус:** принято.

Тесты, зависящие от живых X/CDN URL, Chromium, FFmpeg, FFprobe и сети, отделяются от стабильного локального набора и не должны запускаться по умолчанию вместе с быстрыми unit-тестами.

## ADR-016: Использовать образовательный режим разработки

**Статус:** принято.

Перед изменениями сначала обсуждаются проблема, тип задачи и варианты решения. Готовый код не пишется без явного запроса. После реализации проводится review корректности, архитектуры, читаемости и тестируемости.
